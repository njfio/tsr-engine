## --by repo

Under `--by repo` whole lineages go to one side; with seed 7 the held-out side holds two of them.
Two facts qualify this section's report, and the two blocks after it show both:

- The calibrator is unclipped isotonic regression (`crates/tsr-learn/src/isotonic.rs`): a block of
  calibrate rows that all failed maps to `p=0.000000` and one that all succeeded to `p=1.000000`.
  This bundle prints `p=0.000000` on 20 rows, their raw p from 0.154893 to 0.317539; six are
  held-out rows the report scores, and two of those are overconfident successes. Each adds
  -ln(1e-12) = 27.631021 to the summed log loss, and they are what makes the controller's log loss
  worse than the generator's where it is worse in this report: overall (0.688397 against 0.540648)
  and for the overconfident family (1.442168 against 0.712256). Without those two rows the
  controller's log loss is the lower one, 0.4446 against 0.5451 overall and 0.5391 against 0.7353
  for overconfident (the script's recomputation), and its Brier is lower even with them (0.147054
  against 0.173980; 0.205689 against 0.218037).
- The held-out side has two lineages, `lineage-00` and `lineage-03`. The cluster bootstrap resamples
  lineages, so with two of them each 90% interval is the range between the two lineages' mean paired
  differences: overall -0.063735 and -0.005100, exactly the printed `interval_lo` and `interval_hi`,
  and likewise for every family. The `conclusive` printed for all, calibrated and overconfident says
  only that both lineages' means are below zero; it rests on two lineages, not on a spread of
  resamples.

## Known limitations

These are current behaviour. Each is shown by the block below named after it, except the two
marked "--by repo", which are shown by the last two blocks of that section:

- An `--out` directory the user cannot write exits 1 ("--out is an existing directory the user
  cannot write"), and `fit` and `apply` on a dataset the user cannot write exit 1 too ("fit and
  apply on a dataset the user cannot write"). Root writes a 0555 directory, so as root the script
  runs these commands as uid 65534 through `setpriv`.
- `fit` with `holdout-access.jsonl` as a directory exits 1 (`io: Is a directory`).
- `report` with `<bundle>.report.json` or `<bundle>.report.txt` as a directory exits 1 after
  printing the whole report (its stdout is byte-identical to the pipeline's `report`).
- The `--out` create probe leaves empty ancestor directories behind when a later step refuses:
  `dataset --out .../lim-out/a/b/c`, refused with exit 2 for an empty task index, leaves
  `lim-out`, `lim-out/a` and `lim-out/a/b`.
- `dataset --store` reads the whole file to check its header (`std::fs::read` in
  `crates/tsr-cli/src/train_cmd.rs`; no block can show the read itself), and a store with a valid
  SQLite header (`SQLite format 3\0`) but a corrupt body exits 1
  (`cannot open store ...: sqlite: file is not a database`), not 2.
- The default store path creates an empty store when none exists: with no `--store`, no
  `--events` and `TSR_DB` unset, `dataset` refuses with exit 2 but leaves `.tsr/tsr.db` behind,
  20480 bytes holding 0 events.
- `counts_digest` sits outside the bundle id: editing `unindexed_tasks` alone is refused (exit 2,
  naming the stored and the recomputed digest), but editing it together with its recomputed
  `counts_digest` is accepted, and `fit` prints the same bundle id as the unedited dataset
  (`22b26e5e9bb4...`).
- --by repo: the calibrator is not clipped, so it can print `p=0.000000` or `p=1.000000`, and a
  held-out row with the opposite label adds -ln(1e-12) = 27.631021 to the summed log loss. Two
  held-out overconfident successes at `p=0.000000` are what make the controller's log loss worse
  than the generator's under `--by repo`, overall (0.688397 against 0.540648) and for the
  overconfident family (1.442168 against 0.712256) ("apply --side all (--by repo): the rows the
  calibrator prints at p=0.000000 or p=1.000000").
- --by repo: the held-out side has two lineages, so each paired interval is the range between the
  two lineages' means, and the `conclusive` printed for all, calibrated and overconfident rests on
  two lineages ("apply --side held_out (--by repo): the held-out lineages behind the paired
  intervals").
- The synthetic corpus is not real sessions: every number in this doc comes from
  `fixtures/m4/`, generated by `crates/tsr-learn/src/synth.rs`.

## What the operator runs

The operator's log lives in a store, `.tsr/tsr.db`: the store the hooks write, and the default of
`--store` (with neither `--store` nor `--events`, `dataset` reads `TSR_DB`, else `.tsr/tsr.db`).
Here the store is one the script builds under `target/`: the synthetic generator appends the
corpus to a fresh store as it goes, and `crates/tsr-learn/tests/m4_operator_store.rs` writes that
store where `TSR_M4_OPERATOR_STORE` says and checks that it exports `fixtures/m4/` byte for byte.
The task index and the labels are the fixtures'; on a real log the operator supplies their own.
The commands then run from that directory as the operator runs them from the workspace root (the
binary is named by its path): `dataset` reads `.tsr/tsr.db`, `fit` writes into `models/m4`, a new
directory (`test -e models` exits 1 first), and `verify --rebuild`, `report` and `apply` run on
the result. The dataset has the `--events` dataset's rows, roots and split digest; the bundle id
differs from `22b26e5e9bb4...` only because the source root is the store's `head_root` rather than
the events file's digest, and the report is the pipeline's apart from its `bundle` and
`calibrator` lines.
