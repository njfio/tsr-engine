# Practical completion criteria for the persistent operator engine

A functioning bounded operator tool needs more than passing candidate tests. These criteria are
separate from the PRD's corpus/calibration/research milestones.

| Criterion | Evidence / current limit |
| --- | --- |
| Initialize explicit aims and a bounded source scope | Public CLI supports requirements at initialization, explicit source and byte windows. Operators must verify reused windows against the exact source snapshot. |
| Generate actual candidates from current source and prior outcomes | Installed local models consume public guidance, requirement beliefs and bounded recent outcomes. Small-model failures are retained. No assistant-written candidate is substituted. |
| Preserve authority and freeze expectation before execution | Rust validates source bindings and scope; commit-only/resume and sealed offline execution are exercised. Generator output cannot accept the goal. |
| Distinguish green tests from semantic completion | Source review rejects incomplete metadata even when the named RTS test passes. Acceptance binds current requirements, snapshot and receipt. |
| Turn rejection into a corrective proposal | Operator-published feedback and persistent belief/expectation update the next request. Actual invoice and RTS model attempts demonstrate correction rather than a scripted candidate menu. |
| Preserve several aims across process and episode boundaries | CLI operations reopen stored state; explicit carry imports compatible reviewed outcomes. Invoice follow-up episode preserved product, discount and overflow together. |
| Export only an independently accepted current result | `export --accepted-only` requires a current accepted review. Export never modifies the original repository or publishes changes. |
| Make failures and external authority visible | Timeouts, no-op proposals, invalid output and scope errors stop without silent retries. External spending approval remains separate from local execution. |

This is an operator-assisted system. The operator supplies the legitimate task contract and
publishes shareable feedback; semantic review is not autonomous. This work's reviewer is the
controller assistant, separate from the local generator, rather than an independent human or
formally verified oracle. Local source attestation has task-specific limits.

Remaining practical work includes convenient source/window preflight, better compiler-failure
classification (some currently report `unavailable`), less manual contract preparation, and a
repeatable wider local-task reliability assessment. Local generation is limited to visible units
of 2048 bytes and a conservative context budget; larger tasks require explicit scoped inspection.
The app does not silently expand source exposure, install models, or grant new execution authority.

Neither functional integration nor a successful real RTS repair satisfies M3's minimum 150-task
corpus and baseline interval requirements. Held-out calibration, full-cycle superiority claims,
fine-tuning, long-horizon learning and autonomous goal synthesis remain unverified. The M3
acceptance status remains incomplete; see `docs/PRD.md` B11 and `docs/m3-status.md`.
