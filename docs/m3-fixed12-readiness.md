# Fixed 12-task comparison readiness

Preparation only; no paid inference is authorized or launched in this turn. The selected experiment is 12 constructed mutation tasks from two real repositories, each assigned once to record and once to rules. It is not a historical bug-fix benchmark or an untouched holdout. M3 operational acceptance still requires real outcome evidence; this preparation does not supply it.

Use `docs/m3-fixed12-freeze.json` as the authoritative final manifest, `docs/m3-fixed12-v2-selection.json` as the complete deterministic inventory/ranking, and `docs/m3-fixed12-analysis-plan.md` as the preregistered analysis. ## Controls and interpretation

Recommend 20 requests per arm, 480 total, $60 incremental within $100 cumulative, 1,800 seconds per arm, and 46,800 seconds for controller dispatch/acceptance. The last settled paid baseline is $0.239583. These are ceilings, not a spend target. The conservative 480-request price bound is $53.816832; the budget also retains the existing $2 reservation check. No automatic retries. Unknown transport/billing, uncertain reservations, evidence corruption and containment failures halt remaining arms.

Controller v6 retains headroom checks immediately before dispatch and checks elapsed time after evidence export and before completion. This is not a hard interruptible bound on filesystem operations. Slow-guard and slow-export regressions cover these boundaries. Candidate protected-test tampering remains a native rejection; trusted evidence corruption remains a halt. No oracle acceptance criterion was weakened. A native acceptance accompanied by a policy denial is treated as a review halt under this harness’s stricter contract; that path is not exercised by this offline preflight.

Require 240GiB free initially, maintain 200GiB during execution, and retain workspaces. Build growth can stop the run before all 24 arms finish. No deletion is authorized. Fresh runtime/image/accounting/catalog checks remain mandatory at eventual launch. This turn does not authorize that launch. When separately authorized, invoke the controller as a single exec’d Python process: a retained multi-command shell containing another M3 script can match the existing conservative idle guard. The initial combined read-only-guard/preflight shell encountered this false positive; the subsequent native-preflight command still ran. A clean standalone terminal guard is required before declaring readiness.

Primary analysis uses independently verified successes / 12 for each mode, with explicit reason categories and missingness bounds. All 24 assignments remain visible. Exact paired McNemar calculation is exploratory and only used if all arms are terminal. No pooling with earlier pilots, no superiority claim from this sample.

## Adapter coverage and remaining gaps

Offline native preflight uses the real engine, all selected mutated sources, lineage-specific preparations and images, actual cleared-environment ProcessBroker boundary, production wrapper/schema/transport/accounting logic, and fake HTTP plus a separate zero-charge ledger. Real sockets are forbidden and credentials are replaced before transport. Cases check allowed-file inspection, complete failing-test lists, schema failure closure and rules rejection before inspection. Exports independently validate event roots, CAS, closure and accounting alignment.

Native token/wall/tool/patch budget endings beyond the zero-call regression remain covered by source review and inert tests, not a complete native budget matrix. The offline preflight deliberately does not execute the selected real named tests or final full-suite oracle under the current engine. It does not exercise model-generated repairs, all task-specific compiler/test behavior, successful real-corpus oracle receipts, provider refusal/latency/routing under this workload, or host disk growth across a full live run. Historical corpus qualification and prior synthetic native oracle checks are supporting evidence, not substitutes. These limitations must accompany any launch decision.

## Preserved preflight correction

The first native queue completed all 24 inspection/schema cases and executed the first rules-block case, then its classifier failed on proposal/diagnostic alignment. Actual stored evidence showed a standalone controller Stop, with no proposed Stop candidate. The original failure log and exports are retained. The remaining 11 blocked cases use a separate preflight version; all distinct native cases are re-exported through final controller v6 without repeating successful workloads.

V6 binds exact Stop event reasons and positions, uses source-confirmed proposal counts for each budget ending, rejects unknown budget reasons, and permits zero-response budget closures only with unchanged accounting. It also matches every result denial to the recorded candidate/reason, requires a final unexecuted denied candidate for Rules rejection, and otherwise requires a committed submitted Stop for oracle/tamper endings. Original controller versions remain available; v6 is the sole final launch entrypoint.
