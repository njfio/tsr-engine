# Fixed12 adapter reliability: bounded no-fix assessment

No adapter correctness defect was demonstrated by the retained failures. No production, frozen adapter, engine, oracle, source, accounting, or prior outcome was changed. Introducing a semantic repair without evidence would mislabel a usability experiment as a proven fix. This closes the bounded diagnosis under the requested no-defect alternative.

## Findings

- **Nine truncations:** retained metadata says `finish_reason=length`, string content, and no tool calls. Strict rejection was correct. Raw text was intentionally not retained, so whether output was reasoning, regenerated source, repetition, or another behavior cannot be established. The existing contract already asks for one next action, forbids whole-file regeneration, and permits Stop with only `action`. It does not require the model to emit source when stopping. Increasing output limits or accepting partial output is not justified.
- **One tool-shape failure:** the model returned multiple tool calls despite the one-action contract. The decoder correctly rejected it. A schema `oneOf` and action-specific required fields already exist. Provider enforcement/support is not established by these artifacts; neither schema ambiguity nor a provider defect is demonstrated. No unsupported provider flag or coercion was added.
- **Five edit failures:** each followed one successful edit and then another edit without a fresh inspection. Saved source sizes for arms 3/4/18/19/21 are 12,299/20,086/9,210/9,210/47,881 bytes, below 65,536. This supports a digest mismatch at the saved state rather than oversize. The rejected expected digest and raw request are absent; copied-old, wrong-state and invented digests cannot be distinguished. Native inspection and edit checks hash the same complete bytes; the edit checks again immediately before writing. The controller marks prior inspection stale after a source change. No incorrect hash implementation or accepted stale edit was found. Original composite failure labels remain unchanged.
- **Presentation burden:** the observation can retain an old inspection after editing, alongside `inspection_current=false`; the model also sees a distinct whole-source `source_state`. The prompt explicitly distinguishes that value from the file digest. Copying an opaque digest and managing freshness is a plausible usability burden, not a measured root cause. Extracting a digest from untrusted observation text or silently replacing it with the current file digest would be unsafe.
- **Token/context design:** pair 8 was stopped by a conservative frozen token bound, not a money cap. Rules required 99,099 tokens with 95,553 left; record required 99,119 with 95,989 left. Treating request bytes as input tokens plus framing/output reserve is conservative by design. Large serialized context contributes directly to that bound, but actual next-request tokenizer usage is unknown. Changing accounting, dropping evidence, or enlarging limits is not a demonstrated bug fix.

## Concrete versioned interface recommendation

A future `exact-edit@v4` experiment should have the native controller issue an **inspection handle** bound to task/arm, allowed path, inspected full-file digest and inspection identity. The model selects that handle plus exact old/new spans and its forecast. The controller resolves the handle using trusted structured state, then verifies that the current file still matches the bound digest immediately before applying the unique exact span. After a change, the old handle is stale and must fail; a fresh inspection is required. Cross-task, cross-arm, wrong-path, missing, fabricated and ambiguous handles fail closed. Never infer the handle/digest from repository prose, automatically refresh a stale reference, omit forecasts, merge multiple calls, or repair malformed JSON.

This removes opaque digest transcription without changing edit meaning, authority, freshness, protected tests or the oracle. It is a recommendation, not an implemented or validated version. It would require an additive trusted protocol field and a separately built/pinned native engine; a Python-only substitution based on the observation is not an acceptable shortcut. No new live adapter is launch-ready from this task.

## Small validation plan, after prerequisites

Before any later native launch: establish enough capacity above 200GiB for bounded synthetic outputs without lowering the guard, confirm idle runtime, pin the separately versioned implementation if one exists, and use fake provider responses with socket/credential access disabled. Reuse the established engine and synthetic preparation image where compatible; do not build a real repository. Monitor the same disk floor throughout and stop on containment/integrity uncertainty. No deletion or paid launch is authorized here.

Use seven bounded cases, at most eight broker responses and 120 seconds each: (1–2) full inspect→failing test→one edit→passing test→Stop→independently checked final oracle, once per mode; (3) multiple tool calls rejected; (4) truncated response rejected; (5) stale reference after the first edit rejected; (6) wrong-path/cross-arm reference rejected before mutation; (7) protected-test modification rejected by the independent oracle. These are case specifications, not newly executed tests or an executable frozen launch manifest. For any v4 handle, add unit checks for handle binding, missing/forged handles, exact-span ambiguity and source mutation between resolution and application. Preserve environment clearing, request correlation, forecasts, charge-ledger immutability and all evidence. Require independent review before interpreting a usability improvement or proposing a new paid comparison.

The trusted-handle usability experiment requires an additive native protocol implementation and adequate validation capacity. Current evidence does not justify gate-policy redesign or automatic retries. Broader M3 acceptance remains unchanged by this no-fix assessment.
