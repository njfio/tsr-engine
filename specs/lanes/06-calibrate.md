## Goal

Deliver the calibration half of milestone M4 (Calibrate) of the TSR Decision Engine as docs/PRD.md §B8 and §B11 specify, on branch lane/calibrate from main at fc5c43f, without touching the files of lanes 01, 02, 04 or 05 (see the header). Deliver, in this order:
(1) crates/tsr-learn, depending on tsr-domain and tsr-store only (never tsr-cli) and read-only on the log; only the synthetic generator of (2) appends, to its own fresh store. The common decision event as a pure view over the events: one row per commitment of a gated action — chosen actions only, so an unchosen Proposed candidate is never a row (B8) — with its task, the commitment's event id and 0-based index in the task's log, the action kind, and every forecast on the common event paired to it by tsr_cli::reconstruct's rule (it names the committed candidate; its state_version equals the commitment's index). The common event's id is the one main's hook mints, OutcomeDefId(Hash::of(&[b"task_accepted_in_budget@v1"])), defined once in tsr-learn; lane 04's tsr-forecast mints blake3(name, version) instead, and the operator reconciles the two at merge. Resolve task_accepted_in_budget@v1 per its §B7 row: true when the task closed with criteria met, the promoted diff accepted and no budget ceiling breached; false when it closed with any of the three failing; censored on an operator stop (TaskClosed or Stop with reason operator) or when never reviewed; unresolved while open. Closing and budget come from the log (TaskClosed, Stop { reason: "budget" }); main's log holds no review label, so criteria-met and the diff label come from a labels input (brief's choice; PRD silent on the plumbing): JSONL of { task, criteria_met, diff_label: accepted | rejected | disputed | null, reviewer, recorded_at } — null is never reviewed; disputed resolves false, as lane 04 resolves diff_accepted; a record whose reviewer is not the operator is refused with exit 2 (B8: labels only after review). The terminal outcome labels each row of its task as P(event | state, this action) and credits no action; test_pass is not a label here (B7). Tasks with no index row (item 2) and censored or unresolved rows are excluded from training and scoring and counted in every report. A merge-time adapter will feed lane 04's outcome records and lane 05's oracle verdicts into this input; this lane writes neither.
(2) the synthetic corpus: a seeded generator in crates/tsr-learn/src/synth.rs that drives tsr_store::Store::append with fixed, clock-free timestamps through open → inspect → forecast (generator always, operator on some rows) → commit → dispatch (in_sandbox: true) → execute → close, and writes fixtures/m4/{events.jsonl (the `tsr task export` line format), tasks.jsonl, labels.jsonl}. A task index row is { task, family, lineage, timestamp, clone_group?, tool_ms_ceiling? }, named like lane 05's results so the adapter is trivial. Shape: three families of 120 tasks with known, different generator miscalibration — overconfident (after §B8's example: the generator says 0.9 where the family succeeds about 0.4 of the time when little has been inspected), calibrated, underconfident — plus a fourth family of 20 tasks for the per-family minimum; at least eight lineages so the cluster bootstrap has clusters to resample; two to four gated decisions per task; some censored tasks (never reviewed, operator stop) and some still open. The true acceptance model, each family's distortion, the seed and the counts are documented in the module header and in docs/m4-evidence.md. crates/tsr-cli/tests/m4_corpus.rs regenerates into a temp dir, asserts byte-identity with fixtures/m4/ (TSR_REGEN_FIXTURES=1 rewrites them), and asserts every fixture session satisfies all of tsr_cli::reconstruct's invariants.
(3) features@v1, a versioned spec carried in the bundle. A feature reads only the task's events strictly before the commitment and the task index — never labels, never recorded_at or observed_at (B6), never Committed.decision.utility (main's hook writes a placeholder p_success of 0.5 there; reading it would fabricate a feature). The features: family (one-hot over the fit slice's families); the action kind; inspections so far; distinct inspect targets (distinct args digests — the log holds a digest, not a path — standing in for §B8's "distinct files read" and named for what it measures); patches so far and distinct patch targets (files touched); the generator's raw p on the common event for this commitment as a clipped logit, plus family × generator-logit interactions so a per-family discount is expressible (brief's choice); test runs and failed test runs so far (from Executed exit codes; the log's stand-in for "failing-test count", named so); tool time used over the index's tool_ms_ceiling ("budget fraction used"; a missing indicator where there is no ceiling). The §B8 features main's log cannot supply — patch bytes, failing-test count, whether the failing assertion's file was read, council agreement — are listed in the spec as absent with the reason, for a later schema version; none is imputed.
(4) the dataset, split and leakage probes: `tsr train dataset (--store <db> | --events <events.jsonl>) --tasks <tasks.jsonl> --labels <labels.jsonl> --by time|repo --calibrate <f> --holdout <f> --seed <n> --out <dir>` writes the rows, the split manifest and the data manifest. A row's id is tsr_domain::Hash::of over the commitment's event id, the feature vector and the resolved label with its evidence ids; the data root hashes every row id in canonical order, the training root the fit and calibrate rows. The split is made before any fitting and has three sides — fit (the logistic head), calibrate (isotonic, the support table, the population), held_out (reports only) — brief's choice, since §B9's gate asks for validation-chosen thresholds and isotonic needs rows the head did not see. `--by time` is forward-time by the index timestamp; `--by repo` assigns whole lineages by a seeded shuffle (lane 05's `tsr corpus split` spellings); a task, and a clone group when the index names one, never crosses a boundary. Family rides on every row for per-family scoring, support and the population but is not a split rule: the PRD's holdouts are by time and by repository (§B9). Three probes, each with a planted-leak test it catches and a clean-fixture test it passes: (a) post-action events — every row's features are recomputed from the log truncated before the commitment and any difference fails (planted: an extractor reading the decision's own Executed exit code); (b) label reach — extractors receive no label, by type, and a single feature that perfectly separates the fit slice's labels fails, named (planted: the label copied into a feature); (c) the boundary — no task, clone group or (under repo) lineage on two sides, and under time every held_out task is later than every fit and calibrate task (planted: a forged split manifest). A caught probe exits 2 naming the probe and the row. Every read of held_out rows appends a line to <dir>/holdout-access.jsonl (B9); the split digest covers assignments only, so logging never changes it.
(5) Tier 1 heads and calibrators as §B8 and §B12 specify — logistic regression over the structured features, then isotonic calibration of the common event — hand-rolled in pure Rust: no ML framework, no network, no RNG crate (a small seeded generator such as SplitMix64 lives in tsr-learn). The head is fit on the fit slice with features standardized by fit-slice statistics stored in the spec, a declared L2 penalty, and full-batch updates in a fixed order for a fixed number of iterations; isotonic is pool-adjacent-violators over the head's outputs on the calibrate slice. Only the common event gets a head, as the M4 row says. Minimum data per §B8 ("150 mature episodes per event, ≥ 30 per family"): `tsr train fit` exits 2 with the counts when fit and calibrate hold fewer than 150 tasks with resolved labels, and a family with fewer than 30 stays outside the calibrated population. Applying a bundle yields the controller's `raw p` (the head's output, always) and a `Calibrated { p, calibrator, population }` only for a row whose family is in the population (calibrator = the bundle id; population = the families with their counts); every other row is `uncalibrated`, never a fabricated number. Coefficients and breakpoints live only in the bundle; nothing writes a fitted parameter to the log or the store (AGENTS.md's "no stored weights" governs ledger strengths; the bundle is the PRD's one home for fitted parameters, §B8, §B10).
(6) support and the floor: support is the number of fit- and calibrate-slice episodes of the same family whose every feature lies within a declared window of the query's (binary and one-hot features must match; each numeric feature has a width in the spec) — §B8's "same-family episodes within feature range", the window being the brief's choice since the PRD gives none — returned as tsr_domain::Support and printed `support=<n>`. The bundle carries the support index (each training row's family and feature vector, no labels), so support needs only the bundle. The floor is the operator's (§B12, open): `tsr train fit --support-floor <n>` records it in the bundle, defaulting to Tune::default().support_floor (30), and the report prints, per family on the calibrate slice, coverage and controller Brier at floors 0, 5, 10, 20, 30 and 50 so the operator can set it from evidence. Support is compared with the floor and reported; it never weights, scales or orders anything.
(7) bundles: `tsr train fit <dataset-dir> --out models/<name> [--support-floor <n>]` writes manifest.toml with §B8's fields (data-manifest digest — the data and training roots — feature-schema version, code commit from TSR_CODE_COMMIT or "unknown", seed, calibrator, thresholds: the support floor) plus the split digest and the source root (the store's head_root or the events file's digest), beside head.json, isotonic.json, features.json, split.json and support.json, and prints the bundle id. The id is tsr_domain::Hash::of over each content file's digest and the manifest's content fields — not the code commit, a timestamp or the evaluation report — so the same data and seed give the same id (brief's choice of what the id covers; PRD silent). fit re-runs every probe and refuses when one fails. A bundle is written once, as `draft`; the evaluation report sits beside it naming the id; state transitions and git tags are M5's. `Bundle::load` recomputes every digest and refuses a mismatch; `tsr train verify <bundle> [--rebuild <dataset-dir>]` exits 0, or 2 naming the file whose digest differs, and with --rebuild retrains and compares ids.
(8) the controller against the generator on held-out: `tsr train report <bundle> --dataset <dir> [--seed <n>] [--json]` scores, on held_out rows with a resolved label, the controller's calibrated p against the generator's raw p for the same commitment — Brier, log loss (clip named and printed) and reliability (10 equal-width bins with counts, as lane 04's tsr-forecast does) per forecaster, per family and for the bundle; the operator's raw p is scored beside them where recorded, and forecasts already logged as Forecaster::Controller are scored separately, labeled as logged. The paired difference, controller minus generator, is taken per task (the task is the unit) with a 90% cluster-bootstrap interval over repository lineage (2000 resamples, seeded), INCONCLUSIVE when it spans zero, and `interval n/a` with fewer than two lineage clusters; uncalibrated rows are excluded from the pair and counted. This is §B7's `tsr eval calibration`; lane 05 owns the Eval arm, so it ships as `tsr train report` and the operator wires `tsr eval calibration` to the same function at merge. Every printed number goes through tsr_domain::Proxy with its engineering name (brier, log_loss, support, coverage); a calibrated number prints as `p` with its calibrator version (the bundle id's first 12 hex and features@v1), a raw one as `raw p`, a missing calibrator as `uncalibrated`; families and forecasters are listed in name order, never by score; no output contains "percent certain" or a TSR term followed by a number.
