## Goal

Deliver the corpus and batch-runner half of milestone M3 of the TSR Decision Engine as docs/PRD.md §B9 and §B11 specify, on branch lane/corpus from main, without touching lane 01's or lane 04's files (see the header). The Intuition view's select and tensions steps are NOT this lane's: they need lane 04's ledger and follow in a later lane. Read AGENTS.md, then docs/PRD.md §B3, §B4, §B5, §B8 (Tier 0), §B9, §B10, §B11 M3, then crates/tsr-domain/src/lib.rs, crates/tsr-policy and crates/tsr-cli/src/lib.rs. Deliver, in this order:
(1) crates/tsr-corpus with a Runner trait — `fn run(&self, snapshot: &Path, argv: &[String], limits: &Limits) -> RunResult { exit, stdout_digest, stderr_digest, duration_ms }` — and two implementations: ScriptedRunner (answers from a fixture script; used by every test) and ExecRunner, which invokes the `tsr` binary on PATH as `tsr exec -- <argv>` so every command runs in the sealed sibling sandbox the way the PRD requires (integration tests behind #[ignore] with the reason "needs tsr exec and a container runtime; operator runs it"). Nothing in tsr-corpus runs a repository's tests on the host.
(2) `tsr corpus mine <repo> --out <dir> [--since <rev>] [--suite <cmd>]`: walk the repository's first-parent history (reading git through std::process::Command is allowed here — it reads history, it executes nothing from the repository); for each commit with a parent, run the suite at the parent and at the commit through the Runner and keep the tests that flipped red→green; a task = { id: blake3 of (repo, parent, commit), parent_snapshot: digest, flipped_tests, hidden_diff: CAS digest of the reference diff, family (from the paths touched: crate name, or a declared mapping), lineage: repo, timestamp }; write tasks.jsonl and the CAS under --out. The agent is meant to see a shallow clone at the parent only; the oracle is "flipped tests pass and the full suite does not regress" — encode both as the task's OutcomeDef.
(3) `tsr corpus mutants <repo> --out <dir>`: drive `cargo mutants --list --json` and the kill run through the Runner; each mutant killed by the suite becomes a task { mutated snapshot digest, failing tests, known reversal diff in the CAS, family = (mutation operator, crate), lineage, timestamp }; parse the real cargo-mutants JSON shape (put a captured sample under fixtures/m3/).
(4) `tsr corpus split <dir> --by time|repo --holdout <fraction> --seed <n>`: forward-time by task and lineage-separated by repository; near-clone deduplication by diff similarity (normalized diff shingles, Jaccard ≥ 0.8 → one clone group, never split across the boundary); writes a split manifest with the clone groups and the rule used; leakage probes as tests: a task whose hidden diff appears in another split's parent snapshot, a test added after the task's timestamp, a post-action log — each must be caught. Every holdout access is logged to the manifest (the PRD's "holdout access is logged" rule).
(5) crates/tsr-batch and `tsr task run --mode record|rules --tasks <manifest> --driver scripted|claude-code --out <dir>`: for each task, open an engine task from the corpus task (intent, criteria from the oracle, limits, capabilities), provision the disposable copy at the parent snapshot (through the Runner), drive the session through a Driver trait, run the oracle through the Runner, close the task, and record per-task results { task, system, outcome, generator tokens, tool minutes, wall clock, family, lineage, state root at start }. ScriptedDriver replays a fixture session (a list of candidate actions with their forecasts) by writing the engine's events through tsr-store directly — the way a record-only hook would — and is what every test uses; ClaudeCodeDriver is specified (how the hook payloads arrive, the egress allowlist, the CLAUDE.md instruction to forecast first) and left as a documented stub returning exit 2 with the reason, because the swarm sandbox has no Claude Code and no container runtime. System 1 (record) records and gates nothing; system 2 (rules) runs the Tier 0 controller — inspect until the failing assertion and its call site have been read, then test, then propose, then stop on budget — with every gated action passing through tsr-policy's gate under a RATCHET profile (use crates/tsr-policy as it is; denials are recorded with their reason) and forecast-gated: a RunApprovedTest or ProposePatch without a forecast at the current state version is denied with a message that says what to record. Every recorded session must satisfy tsr_cli::reconstruct::Session's invariants (monotone seq, parents precede children, every gated action has a prior forecast at the same state version, every dispatch reconciled or unresolved); test it over the scripted runs.
(6) `tsr eval baseline <results-dir> [--pair-by task]`: the first numbers with intervals — completion rate, cost per accepted completion (generator tokens + tool minutes + operator minutes, normalized as the PRD states), unsafe attempts blocked, generator calls per task — paired by task between systems, cluster bootstrap by repository lineage, 90% intervals, and the word INCONCLUSIVE when an interval spans zero; a fixed seed makes the report reproducible; every number is a labeled proxy per Appendix A.
(7) fixtures: a tiny git repository built by a test (three commits, one red→green flip, one refactor, one regression) for `mine`; a captured cargo-mutants JSON sample for `mutants`; five scripted tasks and two scripted sessions each for the batch runner; a results directory for `eval baseline` with a known INCONCLUSIVE and a known clear result.
(8) docs/m3-evidence.md quoting every command and its captured output, and a section "What the operator runs" with the exact commands for mining rts and KAMN and for the 150-task target (which needs the host, Docker and lane 01's `tsr exec`), plus README notes for corpus and batch.
