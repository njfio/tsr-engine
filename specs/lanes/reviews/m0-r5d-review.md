## New defects
1. **Low (robustness):** the stale-file recovery is path-based, so two waiters can both enter. exec.rs:480–485 checks the age, then `remove_file(&path)`; a waiter that decided "stale" before another removed and re-created the file deletes the other's live lock, and `Drop` (:511) also removes by path. With a pre-staled lock and 8 or 16 gated waiters it never happened (140 trials). With the window widened by injecting a 30 ms delay on unlink via strace: 10 of 20 trials ran 2–4 containers. So it needs a holder that died leaving the file and simultaneous waiters in a microsecond window, but the result is the double run the lock exists to prevent. Fix: claim a stale file with `rename` to a unique name (only one waiter wins) before unlinking, or write a nonce and have Drop remove only its own.
2. **Low:** an orphaned lock blocks every exec, bare ones included, until the file is 30 s old. A waiter already waiting when the orphan is created has its own deadline (start + 30 s, :466/:488) before the file turns stale (creation + 30 s): reproduced, it exits 2 after 30.04 s with "timed out waiting for the exec lock", ran nothing; a retry succeeds. The timeout is reported as UnknownCandidate (exit 2) and does not say "stale".
3. **Low (tests):** the malformed test (:1171) checks `contains("not a 64-hex candidate id")`, not that stderr is one line, and `committed == 1` does not check the call became a generate proposal; both held when I looked (one line, `generate`).
