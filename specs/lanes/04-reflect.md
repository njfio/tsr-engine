## Goal

Deliver milestone M2 (Reflect) of the TSR Decision Engine as docs/PRD.md §B11 specifies, on branch lane/reflect from main, without touching lane 01's M0 files (see the header). Read AGENTS.md, then docs/PRD.md §B2, §B2.1, §B5, §B6, §B7, §B11 M2 and Appendix A, then crates/tsr-domain/src/lib.rs, crates/tsr-store/src/lib.rs and crates/tsr-cli/src/lib.rs. Deliver, in this order:
(1) crates/tsr-ledger: the Culmination ledger as views over the event log, nothing stored but events. Writes: an Expansion is appended as EventKind::Expanded { expansion } with lineage (parents, catalyzed_by) and the produced Preference content-addressed as blake3(text, scope, parents); statuses are appended as EventKind::StatusSet { preference, status, by }. The active view is a fold: every preference with statuses applied in order (open, fulfilled, superseded(id), withdrawn, overlapping(id), out_of_scope), and admission by source — a preference whose origin is Source::Operator (including rejection reasons) is open on arrival; one whose origin is Source::Generator is in the structure but absent from the active view until an Operator StatusSet(Open) exists for it. Mechanical statuses: fulfilled when the preference's criterion closes (a later return meets it), overlapping when a merge finds a duplicate by normalized text within the same scope; withdrawn and out_of_scope are operator-only (refuse with exit 2 when `by` is not Operator). Collective Reality = the whole log folded; Vibrational Reality = the active view; expose both and the ledger root hash (the store's head_root at the fold).
(2) the Filter in code: from one return, two separate records. Surprise = the forecast residual per forecaster (forecast minus observed return) recorded as an Observed event carrying the domain's Surprise; Contrast = desired minus actual, scored against the task's named open criteria: which were unmet and how (UnmetKind: WrongBehaviour | Regression | Cost | Rejected(reason)) with evidence as event ids. Only a Contrast with at least one unmet criterion may produce an Expansion; a Surprise never does (test it). The produced preference names the dimension the contrast clarified (from UnmetKind and the criterion), never the failed strategy's content; the evidence is referenced, never copied. If Observation lacks Surprise/Contrast variants, add them in a contract: commit touching only tsr-domain.
(3) outcome reconciliation: `tsr task reconcile <task>` finds every Dispatched candidate with neither Executed nor Unresolved and resolves it through a Reconciler trait (first implementation: ToolCheck, which answers from a tool-specific check — a log digest present in the CAS, an idempotency key seen — and otherwise says unknown); an idempotent tool with an unknown outcome is recorded as Unresolved { reason: "unknown after crash; idempotent, retry charged to the same budget" } and may be retried once; a non-idempotent unknown stays Unresolved and blocked until a check resolves it. The crash and cancellation matrix is a test suite over a FakeExecutor implementing tsr_domain::Executor with injectable failure points at intent, send and acknowledgement: at most one Executed per idempotent dispatch across any crash point; a blocked reconciliation otherwise; cancellation appends Unresolved { reason: "cancelled" } and TaskClosed { reason: "operator" }; a post-execution attempt to edit a forecast is rejected by the store (UPDATE → ABORT) while an outcome append succeeds.
(4) review after close: `tsr review <task>` lists the task's returns that await a label and records `accepted`, `rejected --reason <text>` or `disputed` as outcome records — events with Source::Operator, the reviewer, observed_at and recorded_at, statuses pending | observed | censored | missing | disputed | invalid — corrections append a superseding record, never rewrite. The rejection reason is stored apart from tool results and enters the ledger directly as an Operator preference through an Expansion whose Contrast is Rejected(reason) and whose catalyzed_by names the task's open preferences. `tsr review --sample <rate> --seed <n>` selects greens for review with the inverse-probability weight recorded on the record; every failure is listed unconditionally; `tsr review --family <f> --stats` prints the false-accept rate (green but rejected) weighted and unweighted, with the number of labels behind it.
(5) operator entries: `tsr note <task> --text <short>` records Observation::Experience with Source::Operator (its own provenance; never reward truth); the operator's forecast uses the existing `tsr forecast --source operator` and this lane does not change that command. Both appear in the Mirror beside the system's numbers.
(6) crates/tsr-forecast: outcome definitions for the named events of §B7 (test_pass, diff_accepted, task_accepted_in_budget@v1, the four Intuition stages) with horizon, required evidence, censoring rule and intervention rule as data; resolution of a forecast against the task's returns; scoring — Brier, log loss, reliability bins (10 equal-width bins with counts) — per forecaster, per task family, per bundle; the residual series over time per family (the Expansion Dilation proxy, labeled). No calibrator is trained here (M4); `calibrated` stays None and prints as `uncalibrated`.
(7) the Mirror: `tsr reflect <task>` renders one closed episode on one screen in the book's order and nothing else — Desire (intent, criteria with their open/closed state), Imagination (every candidate considered, with its source: generator | council | intuition, and which were excluded by conflict), Belief (the committed candidate with each forecaster's number: `raw p` always, `p` with its calibrator version only when calibrated, otherwise `uncalibrated`; propensity), Return (what came back, its status and evidence digest), and the residual: Surprise per forecaster and Contrast per criterion side by side, never added. Corrections appear as superseding rows. `tsr reflect --family <f>` prints each forecaster's calibration curve (reliability bins and Brier) including the operator's. For any Intuition candidate the Mirror renders its support (the preferences served and the tensions addressed) — "none yet" is a valid screen until M3/M4. `--json` emits the same content as a document for tests. Every number is a labeled proxy per Appendix A; no screen ever renders the four directions as a sequence or prints a TSR term with a number.
(8) fixtures and evidence: thirty closed episodes under fixtures/m2/episodes/ produced by a seeded, documented generator (tests/m2_episodes.rs) that drives the store API through open → propose → forecast (generator, controller, operator) → commit → dispatch → execute → close → review, across three families with different generator calibration; they are synthetic and docs/m2-evidence.md says so — the real thirty come from operator sessions after M3's batch runner; `tsr reflect --family` over them shows the generator's curve; docs/m2-evidence.md quotes every command and its captured output; README gains a short "review and reflect" section.
No tsr-store schema change beyond additive views; no tsr-policy change; conventional commits; fmt and clippy clean.
Operator notes: a create_task refused three times with the same text is a signal, not a retry — stop, post the refusal to the operator, and wait. A passing command is recorded once; do not run a green test again to confirm it. await_task waits at least 60 seconds. Start every command with `export PATH=/usr/local/cargo/bin:$PATH CARGO_HOME=$PWD/.cargo-home` (rust 1.90 with rustfmt and clippy); .cargo-home/ and target/ are build caches — never commit them, exclude them from grep and surveys. Every file write goes through the sandbox, never a host path. A landing commit holds deliverable files only. A review verdict names the file, the line and the behaviour it saw. Dependencies on a Pending task are allowed; a task held past its estimate with no evidence is failed, not extended. Review tasks are created after a landing exists; if create_task refuses with clause (jj), move on and delegate the ready tasks. No reply needed.
